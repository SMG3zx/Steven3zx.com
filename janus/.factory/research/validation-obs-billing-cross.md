## 1. Observability (VAL-OBS-)

These assertions validate Milestone 6 — resource monitoring for running WASM deployments via wasmtime processes, with PostgreSQL time-series storage and dashboard UI.

| ID | Assertion | Verification Method |
|---|---|---|
| VAL-OBS-001 | **CPU tracking per deployment** — the backend collects CPU core-minute usage from each running wasmtime process and persists it in the metrics store with a deployment ID foreign key. | Query `resource_metrics` (or equivalent table) after running a deployment for ≥60 s; confirm CPU rows exist with `deployment_id` and `value > 0`. |
| VAL-OBS-002 | **RAM tracking per deployment** — the backend collects RAM GB-minute usage from each running wasmtime process and persists it alongside the deployment ID. | Same query approach as VAL-OBS-001 for `metric_type = 'ram'`; value must be > 0 after a deployment runs. |
| VAL-OBS-003 | **Disk storage tracking per deployment** — the backend records disk GB-hours consumed by the deployment's working directory and artifact storage. | Confirm disk metric rows exist per deployment; verify value is non-zero when a WASM artifact is present on disk. |
| VAL-OBS-004 | **Network I/O tracking per deployment** — the backend records inbound and egress bytes for each deployment's HTTP endpoint. | Send ≥1 HTTP request to a running deployment, then query network metric; egress bytes must be > 0. |
| VAL-OBS-005 | **Real-time metrics dashboard** — the frontend displays live resource metrics (CPU, RAM, disk, network) for a selected deployment, updating without full page reload. | Open the deployment detail page while a deployment is running; confirm metrics values appear and update within 15 s without manual refresh (SSE or polling). |
| VAL-OBS-006 | **Historical time-series aggregation** — metrics are stored with timestamps and can be queried with time-range filters, returning aggregated (e.g., 1-min or 5-min buckets) data points. | Call the metrics API with `?from=<t1>&to=<t2>&interval=5m`; confirm response contains bucketed data with `timestamp` and `value` fields. |
| VAL-OBS-007 | **Resource limit enforcement** — when a deployment exceeds a configured resource limit (e.g., max RAM), the system either throttles or terminates the process and logs an alert. | Set a low RAM limit for a test deployment, trigger allocation beyond the limit, and confirm the deployment is stopped or constrained and an alert record is created. |
| VAL-OBS-008 | **Alerting thresholds** — users can configure alerting thresholds per deployment or project; crossing a threshold generates a notification or event visible in the dashboard. | Set CPU alert threshold at 80 %; run a deployment that exceeds it; confirm an alert event is created and surfaced in the admin/events API. |
| VAL-OBS-009 | **Per-project aggregated view** — the dashboard provides a project-level summary that aggregates metrics across all deployments belonging to that project. | Create two deployments under the same project; open the project metrics view; confirm totals match the sum of individual deployment metrics. |
| VAL-OBS-010 | **Per-deployment detail view** — the dashboard provides a deployment-level view showing resource time-series for CPU, RAM, disk, and network individually. | Navigate to a single deployment's monitoring tab; confirm four separate metric charts/sections render with non-empty data. |
| VAL-OBS-011 | **Metrics REST API endpoints** — dedicated API routes exist for querying metrics (e.g., `GET /api/deployments/:id/metrics`) with JSON responses conforming to a documented schema. | `curl` the metrics endpoint for a known deployment; confirm HTTP 200 and JSON body containing `cpu`, `ram`, `disk`, `network` fields. |
| VAL-OBS-012 | **Metrics collection resilience** — if the wasmtime process crashes, the last collected metrics are still persisted and the collector does not crash or leak goroutines. | Kill a wasmtime process externally; confirm the metrics collector logs the loss, does not panic, and previously recorded metrics remain queryable. |

## 2. Billing (VAL-BIL-)

These assertions validate Milestone 7 — Stripe metered usage billing with 4 dimensions, webhook handling, and frontend billing dashboard. All Stripe interactions use test-mode keys.

| ID | Assertion | Verification Method |
|---|---|---|
| VAL-BIL-001 | **Subscription creation on signup** — when a new user completes registration, the backend creates a Stripe Customer and a Subscription with 4 metered price items (CPU, RAM, disk, network). | Register a new user; query Stripe test API (`GET /v1/customers?email=...`); confirm customer exists with a subscription containing exactly 4 items linked to the 4 meter-backed prices. |
| VAL-BIL-002 | **Four metered dimensions configured** — Stripe Meters exist for `janus_cpu_minutes`, `janus_ram_gb_minutes`, `janus_disk_gb_hours`, and `janus_network_egress_gb`, each with `sum` aggregation. | `GET /v1/billing/meters` via Stripe API; confirm all 4 meters are present with correct `event_name` and `default_aggregation.formula = "sum"`. |
| VAL-BIL-003 | **Usage reporting pipeline** — the backend periodically (every 1-5 min) batches observability metrics and sends Stripe Meter Events with correct `event_name`, `stripe_customer_id`, `value`, and idempotency `identifier`. | Run a deployment for 10 min; query `GET /v1/billing/meters/:id/event_summaries`; confirm aggregated usage > 0 for CPU and RAM meters. |
| VAL-BIL-004 | **Billing dashboard — current usage** — the frontend billing page displays current-period usage across all 4 dimensions with human-readable units and estimated cost. | Navigate to `/billing` in the frontend; confirm a "Current Usage" section shows CPU (core-min), RAM (GB-min), disk (GB-hr), network (GB) with non-zero values after running a deployment. |
| VAL-BIL-005 | **Invoice viewing** — the frontend billing page lists past invoices with status (paid/open/draft), amount, and a link to the Stripe-hosted invoice PDF or page. | After at least one billing cycle or manual invoice finalization, navigate to the invoices section; confirm ≥1 invoice row with status and amount displayed. |
| VAL-BIL-006 | **Payment method management** — users can add, view, and remove payment methods (cards) through the billing UI, either natively or via Stripe Customer Portal redirect. | Click "Manage payment methods"; confirm either a Stripe Customer Portal session opens or an in-app form appears allowing card CRUD. |
| VAL-BIL-007 | **Subscription lifecycle — pause and resume** — a user can pause their subscription (stops new billing) and resume it; pausing does not delete existing resources but may stop active deployments. | Pause subscription via billing UI; confirm Stripe subscription status = `paused`; resume it; confirm status = `active`. |
| VAL-BIL-008 | **Subscription lifecycle — cancel** — a user can cancel their subscription; cancellation stops billing at period end and triggers deployment teardown after the period. | Cancel subscription; confirm Stripe shows `cancel_at_period_end = true`; after period end, confirm deployments are stopped. |
| VAL-BIL-009 | **Webhook handling — payment succeeded** — the backend processes `invoice.paid` webhook events and updates the user's billing status to good standing. | Send a test webhook event (`stripe trigger invoice.paid`); confirm the backend logs successful processing and user status is active. |
| VAL-BIL-010 | **Webhook handling — payment failed** — the backend processes `invoice.payment_failed` events, flags the user's account, and surfaces a warning in the frontend. | Trigger `invoice.payment_failed` test event; confirm the backend records the failure and the user sees a payment-failed banner on next dashboard load. |
| VAL-BIL-011 | **Free tier or trial period** — new users receive an initial free tier (e.g., N free compute-minutes) or trial period; usage within the free allowance does not generate charges. | Register a new user; confirm the Stripe subscription has a `trial_end` date or that a billing credit is applied; run a small deployment and confirm the invoice amount is $0 within the free allowance. |
| VAL-BIL-012 | **Stripe Customer Portal redirect** — clicking "Manage Billing" in the frontend redirects the user to Stripe's hosted Customer Portal with a valid session URL and correct `return_url` back to Janus. | Click the portal link; confirm browser navigates to `billing.stripe.com` with session token; confirm the return URL points to the Janus billing page. |

## 3. Cross-Area Flows (VAL-CROSS-)

These assertions validate end-to-end flows that span multiple milestones (auth, projects, builds, deployments, domains, observability, billing, frontend).

| ID | Assertion | Verification Method |
|---|---|---|
| VAL-CROSS-001 | **Full lifecycle: sign-up → first invoice** — a new user can sign up, create a project, import a repo, trigger a WASM build, deploy the artifact, attach a custom domain, observe resource metrics, and receive a first invoice reflecting metered usage. | Execute the complete flow sequentially (API or UI); after ≥1 billing period (or manual invoice finalization), confirm the Stripe invoice contains line items for ≥1 metered dimension with amount > 0. |
| VAL-CROSS-002 | **Deploy + domain + monitor + bill** — deploying a service with a custom domain results in: (a) the domain resolving to the deployment, (b) resource metrics being collected, and (c) usage charges appearing on the next invoice. | Deploy with custom domain; curl the domain to confirm it serves the WASM app; check the metrics API for non-zero values; check the Stripe upcoming invoice for line items. |
| VAL-CROSS-003 | **Multiple deployments → aggregated billing** — a user with N active deployments sees a single Stripe subscription with usage summed across all deployments per meter dimension. | Create 2+ deployments; let them run; query Stripe meter event summaries; confirm the reported values aggregate usage from all deployments (not just one). |
| VAL-CROSS-004 | **Auth gates all protected resources** — unauthenticated requests to projects, builds, deployments, billing, domains, and monitoring endpoints return HTTP 401. | For each protected route family (`/api/projects`, `/api/builds`, `/api/deployments`, `/api/billing`, `/api/domains`, `/api/metrics`), send a request without an auth token; confirm all return 401. |
| VAL-CROSS-005 | **Deployment deletion stops billing and releases domain** — when a user deletes a deployment: (a) the wasmtime process is terminated, (b) resource metrics collection stops for that deployment, (c) usage reporting to Stripe ceases for that deployment, and (d) any associated custom domain is released. | Delete a running deployment; confirm the wasmtime process is gone (`ps` / process map); confirm no new metric rows are inserted; confirm no new Stripe meter events reference that deployment; confirm the custom domain's Cloudflare record is removed. |
| VAL-CROSS-006 | **Frontend navigation completeness** — from the authenticated dashboard, a user can navigate to ALL feature areas (projects, builds, deployments, domains, monitoring, billing) using only in-app links and menus, without typing URLs manually. | Using browser automation (Playwright/agent-browser), log in and verify that clickable navigation elements exist and lead to each of the 6 feature areas; confirm each page renders meaningful content (not 404 or blank). |
| VAL-CROSS-007 | **Error propagation: backend → frontend** — when a backend operation fails (e.g., build failure, deployment crash, Stripe error), the error is returned with an appropriate HTTP status and a user-friendly message that the frontend displays in a toast, banner, or inline error. | Trigger a known failure (e.g., build a repo with unsupported language); confirm the API returns 4xx/5xx with a JSON `error` field; confirm the frontend renders the error message visibly. |
| VAL-CROSS-008 | **Observability feeds billing accurately** — the total metered usage reported to Stripe for a deployment matches (within ±5 %) the metrics stored in the local observability database for the same time window. | Query the local metrics DB for a deployment's CPU core-minutes over a 1-hour window; query Stripe meter event summaries for the same customer/meter/window; confirm values differ by ≤5 %. |
| VAL-CROSS-009 | **Subscription pause halts deployments and billing** — when a user pauses their subscription, all active deployments are stopped, metrics collection halts, and no further Stripe meter events are sent until the subscription is resumed. | Pause subscription; confirm all user deployments transition to `stopped` status; confirm no new meter events appear in Stripe; resume subscription and confirm deployments can be restarted. |
